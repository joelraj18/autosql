Part 1 · every upload rides this line

Learn the schema and the grain

Stop 1

Load: text first, then types

Reading straight into numbers loses codes like 05021; reading straight into text loses dates. So every column is read as text and typed afterwards.

  • IFwhole numbers with no leading zero → integer; with ≤ 4 decimals → decimal
  • IF≥ 95% of values parse with one date format → DATE (or TIMESTAMP when times appear); no day above 12 in m/d vs d/m → warn: ambiguous
  • IF≥ 95% are numbers once a currency sign, thousands separators, % and (12.50) are read → number, with the sign kept as the unit; -, #N/A → NULL
  • ALWAYSnames → snake_case (OrderID → order_id); a CSV is a table, each Excel sheet is a table, a ZIP holds up to 50 of them

8 CSVs; 75 columns renamed; 18 postal codes keep their leading zero; OrderDate becomes a DATE.

Stop 2

Roles and the primary key

A column's type is how it is stored; its role is how SQL should use it: join on an identifier, add up a measure, group by a dimension. The key says what one row is.

  • IFnamed like …_id / …_code / …_no → identifier; a number → measure (price, quantity, discount, charge, amount); 2–50 labels → dimension; "Very Bad … Very Good" → rating (1–5)
  • KEYone unique, never-empty column (scored by name and position) → single; else two IDs together → composite (order lines); else an ID unique once exact copies are removed, or in ≥ 90% of rows → meant to be the key: duplicates are listed and removed with ROW_NUMBER()
  • PROOFCOUNT(*) vs COUNT(DISTINCT key) per table, in SQL

order_details: (order_id, product_id), one row per order line. customers: customer_id beats the also-unique company_name.

order_id, one row per order. customer_feedback → rating; quarter_number → a date part, checked against order_date.

employee_id, one row per employee.

Stop 3

Foreign keys and cardinality

Matching values prove little: the codes 1, 2, 3 are valid keys of many tables. Names are strong evidence; values alone are only a suggestion.

  • IFnamed like another table's key and ≥ 95% of values found there → used
  • IFboth columns of a two-column key (region + store_no) and ≥ 95% of the pairs found → used, joined on both
  • IFreports_to / manager_id / parent_id, all found in the same table → used (self-reference)
  • IFvalues only: all found, and equal value sets or a shared name stem → suggested: you tick it
  • THENchildren per parent (1:1 or 1:N); parent numbers summed before and after the join → fan-out

Stop 4

Validate before analysing

Duplicates, NULLs, orphans and missing days all change totals without raising an error.

  • CHECKduplicates: GROUP BY key HAVING COUNT(*) > 1
  • CHECKNULLs: COUNT(*) - COUNT(col) for every column; impossible values: a negative price, a discount out of range (negative quantities: likely returns)
  • CHECKdates: MIN / MAX, rows per period; a first or last period with < 90% of its days → partial
  • CHECKorphans: LEFT JOIN … WHERE parent.key IS NULL, and parents nobody points at (NOT EXISTS)
  • STOP IFno table has any rows

0 duplicates, 0 orphans, no impossible values; 2 customers never ordered; 21 orders not shipped; 1998-Q2 partial (36 of 91 days).

No NULLs; 4 complete quarters; quarter_number agrees with order_date on every row.

Going further by hand

Each snippet runs on the Northwind project as exported by the app (tables plus the order_facts / line_facts views), and was tested on MySQL 8.4 and PostgreSQL 16.

Recursive CTE: the org chart

Walk a self-reference to any depth. Same SQL in MySQL 8 and PostgreSQL.

WITH RECURSIVE org AS (
    SELECT employee_id, last_name, reports_to, 1 AS depth
    FROM   employees
    WHERE  reports_to IS NULL
    UNION ALL
    SELECT e.employee_id, e.last_name, e.reports_to, o.depth + 1
    FROM   employees e
    JOIN   org o ON e.reports_to = o.employee_id
)
SELECT * FROM org ORDER BY depth, employee_id;

Median per segment

The app reports the overall median order (943.25). Per category: PostgreSQL has an ordered-set aggregate; MySQL needs window functions. Both give Beverages a median line of 251.55.

-- PostgreSQL
SELECT category_name,
       ROUND(PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY revenue)::numeric, 2) AS median_line_revenue
FROM   line_facts
GROUP  BY category_name
ORDER  BY category_name;

-- MySQL 8 (also runs on PostgreSQL: / 2.0 never truncates)
WITH ranked AS (
    SELECT category_name, revenue,
           ROW_NUMBER() OVER (PARTITION BY category_name ORDER BY revenue) AS row_num,
           COUNT(*) OVER (PARTITION BY category_name) AS cnt
    FROM   line_facts
)
SELECT category_name, ROUND(AVG(revenue), 2) AS median_line_revenue
FROM   ranked
WHERE  row_num IN (FLOOR((cnt + 1) / 2.0), FLOOR((cnt + 2) / 2.0))
GROUP  BY category_name
ORDER  BY category_name;

Pivot with conditional aggregation

Years as columns, one row per category. Same SQL in both dialects.

SELECT category_name,
       ROUND(SUM(CASE WHEN order_year = 1996 THEN revenue ELSE 0 END), 2) AS revenue_1996,
       ROUND(SUM(CASE WHEN order_year = 1997 THEN revenue ELSE 0 END), 2) AS revenue_1997,
       ROUND(SUM(CASE WHEN order_year = 1998 THEN revenue ELSE 0 END), 2) AS revenue_1998
FROM   line_facts
GROUP  BY category_name
ORDER  BY revenue_1997 DESC;

Gaps and islands: months in a row

Consecutive values minus ROW_NUMBER() are constant within a streak. BERGS and QUICK ordered 8 months in a row.

WITH months AS (
    SELECT DISTINCT customer_id,
           order_year * 12 + MONTH(order_date) AS month_index
           -- PostgreSQL: EXTRACT(MONTH FROM order_date)::int
    FROM   order_facts
),
islands AS (
    SELECT customer_id, month_index,
           month_index - ROW_NUMBER() OVER (PARTITION BY customer_id
                                            ORDER BY month_index) AS island
    FROM   months
)
SELECT customer_id, COUNT(*) AS months_in_a_row
FROM   islands
GROUP  BY customer_id, island
ORDER  BY months_in_a_row DESC, customer_id
LIMIT  5;

Date spine: months with no orders show 0

GROUP BY only returns months that have rows; join to a calendar instead.

-- MySQL 8: a recursive CTE builds the calendar
WITH RECURSIVE spine AS (
    SELECT DATE '1996-07-01' AS month_start
    UNION ALL
    SELECT month_start + INTERVAL 1 MONTH FROM spine
    WHERE  month_start < DATE '1998-05-01'
)
SELECT s.month_start, ROUND(COALESCE(SUM(f.revenue), 0), 2) AS revenue
FROM   spine s
LEFT   JOIN order_facts f
       ON  f.order_date >= s.month_start
       AND f.order_date <  s.month_start + INTERVAL 1 MONTH
GROUP  BY s.month_start
ORDER  BY s.month_start;

-- PostgreSQL: FROM generate_series(DATE '1996-07-01', DATE '1998-05-01',
--                                  INTERVAL '1 month') AS s(month_start)
--             and INTERVAL '1 month' in the join

Upsert: insert or update

Reloading a day must replace it, not duplicate it.

-- MySQL 8.0.19+
INSERT INTO daily_revenue (day, revenue)
VALUES (DATE '1998-05-06', 250.00) AS new
ON DUPLICATE KEY UPDATE revenue = new.revenue;

-- PostgreSQL
INSERT INTO daily_revenue (day, revenue)
VALUES (DATE '1998-05-06', 250.00)
ON CONFLICT (day) DO UPDATE SET revenue = EXCLUDED.revenue;
